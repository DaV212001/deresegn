1. SECTION ONE 
1.1 INTRODUCTION 
The Minister of Revenue is actively working on implementing an advanced electronic invoice 
management system designed to modernize the invoicing process, enhance transparency, and 
uphold integrity in financial transactions. This initiative aims to significantly improve operational 
efficiency in tax collection while ensuring a more seamless and reliable approach to managing 
invoices. The introduction of this system is expected to bring substantial benefits to both taxpayers 
and the Ministry. 
For taxpayers, the system simplifies adherence to tax regulations, minimizes paperwork, and 
reduces administrative burdens associated with financial transactions. By automating and 
streamlining processes, it eliminates many of the complexities traditionally i nvolved in invoicing 
and tax compliance. As a result, businesses and individuals can manage their tax -related 
responsibilities with greater ease, accuracy, and efficiency. 
From the Ministry’s perspective, the system plays a crucial role in strengthening ta x compliance 
by ensuring that financial transactions are more transparent and traceable. Additionally, it 
facilitates more effective and timely tax collection, reducing the risk of tax evasion and improving 
overall revenue generation. By leveraging technol ogy, the Ministry is taking a proactive step 
toward a more efficient, transparent, and accountable tax administration system that benefits all 
stakeholders involved.

1.7 EIMS PROCESS FLOWS 
1.7.1 List of Invoice Processes 
EIMS is the electronic invoice registration, cancellation and verification system of the Ministry of 
Revenue of The Federal Democratic Republic of Ethiopia. The main processes of EIMS are: 
1. Authenticate with EIMS for API communication 
2. Enable taxpayer systems send requests to register invoices via API and receive clearance of 
invoice with unique Invoice Registration Number (IRN) and QR Code 
3. Enable taxpayer systems send request to cancel invoices via API and receive confirmation of 
cancellation 
=== PAGE 11 ===
 
 
 
4. Enable taxpayer systems send bulk registration/cancellation requests via API or File uploads 
and receive results of their requests via Call Back API or File Downloads 
The following sub -sections provide high -level overview of the above process flows which are 
explained in detail in other related documents that are listed in section 3.0. 
1.7.2 Authentication 
Taxpayer Systems need to authenticate with EIMS Authentication APIs us ing AOUTH2 for 
communicating through REST end points. For authentication taxpayer systems need to be 
configured with API Key, Client ID and Client Secret which will be provided via secure 
communication during the on -boarding process. In addition, taxpayer System administrators can 
change these credentials via the EIMS taxpayer portal. 
Upon successful authentication, the Electronic Invoice Management System (EIMS) issues a JWT 
token with a validity of three hours. Additionally, the Taxpayer System receives a  refresh token, 
allowing it to renew the JWT token without requiring re -authentication. The specifics of this 
process are outlined in the security specifications section of this document.

1.7.4 Invoice Cancellation 
Process 
Taxpayer systems can submit a request to cancel an invoice, which will be verified by EIMS based 
on applicable rules and regulations for invoice cancellations. If the request meets the validation 
criteria, a cancellation confirmation will be issued . Invoice cancellation is only permitted for 
invoices registered in EIMS and must comply with specific rules, including the maximum 
allowable time between issuance and cancellation, as well as daily and monthly limits on the 
number of cancellations. 
A cancellation request is automatically processed if it meets the predefined rules and falls within  
the permitted daily and monthly cancellation limits. However, if the request exceeds these limits, 
it will be subject to manual review before any further action is taken. This manual review ensures 
compliance with regulations and prevents excessive or illegal cancellations. The validation process 
helps maintain the integrity of the system by enforcing restrictions on the number of cancellations 
allowed within a given period.

1.7.5 Batch Registration and Cancellation 
EIMS has provision for batch registration and cancellation using two different approaches, though 
bulk registration/cancellation APIs and through bulk registration/cancellation request files. 
1.7.5.1 Bulk Registration and Cancellation API 
With bulk registration and cancellation APIs, a number of requests are sent to EIMS and EIMS 
processes and responds to these requests asynchronously. Due to the nature of asynchronous 
responses, taxpayer systems will have to make ready a web call back interface that will receive 
results of the bulk registration/cancellation requests. Different rules of regi stration as well as 
cancellation are applied during bulk registration/cancellation than those for single invoice 
registration/cancellation.

2.1 INVOICE REGISTRATION 
2.1.1 PURPOSE 
A primary function of the Electronic Invoice Management System (EIMS) is invoice registration, 
which plays a vital role in managing invoices and ensuring tax compliance. This section provides 
a general overview of how invoice registration requests are submitted to EIMS, emphasizing the 
overall process rather than the specific attributes of the invo ice registration object. For a 
comprehensive understanding of these attributes, including the necessary fields and their formats, 
this section offers a detailed guide. This helps taxpayers accurately register invoices in the system 
while adhering to compliance requirements. 
2.1.2 OVERVIEW 
This section provides an overview of the integration requirements for submitting a single e-
invoice to the Ministry of Revenue (MoR) e -invoice endpoint. It outlines the essential steps 
and compliance standards needed to ensure a  seamless and successful process. This section 
covers the following key areas: 
 Request JSON Schema: The structure and validation rules of the e -invoice request 
payload. 
 Digital Signing Requirements: How to digitally sign the request and attach the certificate. 
 Response Types: 
o Success Response (200): Returned when an invoice registration is successful. 
o Schema Validation Error Response (400): Returned when the request JSON does not 
meet the schema definition. 
o Rule Validation Error Response (406): Returned when the JSON schema is correct 
but the invoice fails business/rule validation checks. 
 
2.1.3 REQUEST SCHEMA 
The request must be structured as a JSON object and include three primary properties: request, 
signature, and certificate. The request object must follow the specified JSON schema to ensure 
=== PAGE 19 ===
 
 
 
proper formatting and data integrity. Additionally, the signature and certificate are essential 
components that must be included to verify the authenticity of the digital signature. These 
elements work together to ensure the security and integrity of the request, confirming that it 
has not been altered and originates from an authorized source. 
2.1.3.1 Top Level Structure 
 
 
{ 
  "$schema": "http://json-schema.org/draft-07/schema#",

} 
Key Points: 
 Request: Contains the invoice details including DocumentDetails, BuyerDetails, 
SellerDetails, ItemList, V alueDetails, PaymentDetails, SourceSystem, ReferenceDetails, and 
TransactionType. Details of this is provided in subsequent documents. 
 Signature: A digital signature string generated by the client's private key over the 
canonicalized request object. 
 Certificate: A Base64-encoded certificate (e.g., X.509) used to verify the digital signature.

2.1.3.2 Digital Signing Requirements 
Canonicalization of Request Object:  
 Before signing, the request object must be canonicalized (e.g., using a deterministic JSON 
serialization without extra whitespaces or formatting differences). 
Signature Generation:  
 Use the private key associated with the provided certificate. Compute the digital signature (e.g., 
using RSA or ECDSA) over the canonicalized request JSON (not including the Signature and 
Certificate properties).  
 Base64-encode the resulting signature. 
Attach Signature and Certificate: 
 Signature: The Base64-encoded digital signature string. 
 Certificate: The Base64-encoded client certificate that corresponds to the private key used for 
signing. 
Validation on the Server Side: 
 The server will verify that the signature is valid for the given request using the provided 
certificate. 
 Any mismatch or invalid signature will cause the request to be rejected.

3 SECTION THREE 
3.1 INVOICE REGISTRATION SCHEMA DETAIL 
3.1.1 PURPOSE  
For the Electronic Invoice Management System (EIMS) and the taxpayer system to work 
seamlessly and exchange information effectively, it's crucial to follow a predefined JSON schema. 
This integration document is designed to guide technical teams in connecting their systems to the 
e-invoicing platform using the provided schema. It explains how to correctly structure invoice 
requests, understand the necessary conditions, and validate data before submitting it. By following 
these instructions, can ensure smooth communication between taxpayer systems and EIMS, 
helping maintain accuracy and reliability in the invoicing process. 
3.1.2 OVERVIEW OF THE E-INVOICING SCHEMA 
The provided schema helps ensure that data remains consistent, accurate, and compliant for 
electronic invoices, credit notes, debit notes, and other related documents. By following this 
schema, taxpayer can stay in line with local e -invoicing regulations, reducing the chances of 
errors and ensuring that all documents meet the required standards. This leads to a more 
efficient invoicing process and reduces compliance risks, making the entir e system more 
reliable and easier to work with. 
3.1.3 HIGH-LEVEL ARCHITECTURE 
3.1.3.1 SYSTEM COMPONENTS 
 Your ERP/CRM/POS: Generates invoice data. 
 E-Invoicing Validation Service: Applies the JSON schema rules. 
 E-Invoicing: Receives and processes validated invoices. 
 
 
 
 
=== PAGE 45 ===
 
 
 
3.1.3.2 DATA FLOW 
1. Your system creates the invoice JSON object. 
2. Validate the object against the schema. 
3. Submit the validated invoice to the EIMS API. 
4. Receive an Invoice Reference Number (IRN) and QR Code or error   messages. 
5. Store the IRN and invoice data. 
3.1.4 SCHEMA OVERVIEW 
3.1.4.1 JSON Schema Version 
The schema is based on JSON Schema draft-07, so it's crucial to ensure that your validator supports 
this version. This will help guarantee that the data is properly validated and meets the required 
standards. Using the correct version of the schema will prevent potential issues and ensure 
everything functions smoothly. 
3.1.4.2 Top-Level Elements 
Key properties include: 
 TransactionType 
 DocumentDetails 
 SourceSystem 
 SellerDetails 
 BuyerDetails 
 ItemList 
 PaymentDetails 
 ValueDetails 
 ReferenceDetails 
All these have specific constraints and sometimes conditional requirements.

3.1.4.3 Key Entities and Their Properties 
TransactionType 
 Description : Indicates the type of transaction (e.g., B2B, B2C, G2C). 
 Purpose : To classify the nature of the transaction between the seller and buyer. 
 Format : String with a maximum length of 3 characters. 
 Example Values : "B2B", "B2C", “B2G","G2B","G2C"," 
 Conditional Validations : 
 If TransactionType is not "B2C" or "G2C", then BuyerDetails.Tin is required and must be 
a non-null string. 
 If TransactionType is "B2C" or "G2C", then BuyerDetails.Tin can be null, and 
BuyerDetails.VatNumber must also be null. 
DocumentDetails 
 Description : Contains metadata about the document, such as its type, number, date, and reason (if 
applicable). 
        Sub-Fields 
 Type 
 Purpose : Specifies the type of document (Invoice (INV), Credit Note (CRE), Debit 
(DEB) Note, Interim (INT), Retainer (RTN), Final (FIN), Mixed Invoice (MIX), 
Intercomany (INC), Proforma (PRF), Overdue (OVD)). 
 Format : A string with a maximum length of 3 characters. Example: "INV", "CRE", 
"DEB". 
 Conditional Validation : If Type is "CRE", "DEB", "INT", or "FIN", then Reason is 
required. 
 DocumentNumber 
 Purpose : Sequential number assigned by the seller to the document. 
 Format : A string with a length between 1 and 100 characters. Example: "1234". 
 Date 
 Purpose : Date and time when the document was generated. 
 Format : ISO 8601 datetime string. Example: "15-09-2023T14:30:00". 
 Reason 
 Purpose : Reason for issuing the document (applicable for credit/debit notes). 
 Format : A string with a length between 3 and 100 characters. Example: "Test reason". 
 Conditional Validation : Required if Type is "CRE", "DEB", "INT", or "FIN". 
SourceSystem 
 Description : Identifies the system that generated the invoice.

2. SECTION FOUR 
2.1.  BULK INVOICE REGISTRATION  
2.1.1. PURPOSE  
In the Electronics Invoice Management System (EIMS), there are two main ways to register 
invoices: single invoice registration and bulk (or batch) invoice registration, which allows you to 
register multiple invoices at once. This section is here to guide through the process of bulk invoice 
registration, making it easier to handle large numbers of invoices efficiently. 
This section of the document provides clear, step-by-step instructions on how to register invoices 
in bulk. It also offers helpful tips, best practices, and advice for tackling common challenges, 
ensuring that you can smoothly and accurately manage the bulk registration process without 
unnecessary issues. 
2.1.2. OVERVIEW BULK INVOICE REGISTRATION 
Bulk e-invoice registration is a helpful feature that allows taxpayer systems to register multiple 
invoices all at once. This is especially useful in situations where the system needs to gather invoice 
documents locally and then register them in bulk at a later time. It’s designed to make the process 
more efficient, particularly when dealing with large numbers of invoices. 
This feature is perfect for businesses that need to register invoices in batches, whether they’ve 
accumulated a group of invoices over time or need to process a large volume all at once. Below, 
we’ll cover some important things to keep in mind when using bulk invoice registration to ensure 
everything goes smoothly. 
1. The number of invoice documents that can be sent for bulk registration at once is 
governed by a rule set  
2. Taxpayer systems when sending bulk invoice registration request will receive 
conversation id if all the invoice documents in the request comply with the schema 
standard of EIMS electronic invoice registration 
=== PAGE 61 ===
 
 
 
3. EIMS will process bulk invoice registration asynchronously and use a call back url and 
provided conversation id to notify TP systems of the invoice registration result. In case of 
failed call back handling or if the sales register machine cannot receive call back from 
EIMS, it can consume the API endpoint availed by EIMS to fetch status and response 
contents by conversation ID. 
4. Invoice registration failures related to rule evaluation will be handled separately for each 
invoice and appropriate responses related to each invoice will be part of the bulk invoice 
registration response 
2.1.3. HIGH-LEVEL ARCHITECTURE 
2.1.3.1. System Components 
 Your ERP,CRM, POS or billing system: Generates bulk invoice registration data. 
 E-Invoicing Validation Service: Applies the JSON schema rules and if the rules are 
satisfied a conversation id will be returned. 
 EIMS backend: Receives and processes validated invoices, store the results and call 
the provided call back url to provide the result 
 Taxpayer System: will receive the results and process. 
 
The taxpayer must retain the received IRN and QR Code for each invoice or receipt. Tax auditors 
and/or supervisors will request the taxpayer to provide the list of invoices and receipts against the 
list of received IRNs.

2.1.3.2. Data Flow 
1. Taxpayer system creates the bulk invoice JSON object. 
2. EIMS validate the object against the schema. 
3. EIMS will send conversation id for asynchronous communication reference, if the schema 
validation passes. 
4. Taxpayer system will receive results of bulk registration through call back URL.

3. SECTION FIVE 
3.2 INVOICE CANCELLATION 
3.2.1 PURPOSE  
The Electronics Invoice Management System (EIMS) and the Taxpayer System need to work 
together smoothly and efficiently to ensure that information is exchanged without any delays. To 
make this happen, it’s essential for both systems to follow a set of predefined integration standards 
that ensure everything stays consistent and reliable. 
This section is designed to give supplier and taxpayer  clear and practical guidance on how to 
integrate with EIMS specifically for handling invoice cancellations. Invoice ca ncellations can 
happen for many reasons throughout the business process—whether it’s due to changes in an order, 
customer disputes, or simple mistakes in the invoicing. EIMS is built to handle these situations 
seamlessly by providing a secure and easy-to-use API interface for cancellations. 
By using this API, businesses can manage cancellations quickly and efficiently, ensuring 
compliance with regulations while keeping their records accurate and up to date. This section of 
the document  aims to help developers implement this integration easily so businesses can 
streamline their processes and focus on what they do best. 
The cancellation request is automatically processed if it adheres to the predefined daily and 
monthly cancellation limits and falls within the allowed time frame between invoice registration 
and cancellation. If the limits are exceeded or the request is outside this timeframe, it will undergo 
manual review. 
3.2.2 OVERVIEW OF INOICE CANCELATION 
The main purpose of the Electronics Invoice Management System (EIMS) is to handle essential 
tasks like registering, verifying, and canceling invoices. Among these, invoice cancellation 
happens quite often. This is because, in the day -to-day operations of a business, it’s normal to 
encounter mistakes or the need for changes when generating invoices. 
=== PAGE 76 ===
 
 
 
Invoice cancellations are initiated by Taxpayer (TP) systems for invoices that have already been 
registered in EIMS. To process a cancellation, the Taxpayer system needs to provide the Invoice 
Reference Number (IRN) of the invoice they want to cancel, along with a clear reason for why the 
cancellation is necessary. 
The cancellation process follows a set of defined steps to ensure everything is handled accurately 
and in line with the rules. These steps help businesses make corrections or adjustments efficiently, 
without disrupting their workflows or falling out of compliance with regulations. 
1 Request for invoice cancellation is initiated by Taxpayer system 
2 EIMS validates the request JSON against cancellation schema 
3 EIMS process the cancellation request processing it through various cancellation rules 
including but not limited to 
 Allowed number of cancellations in a day or a month 
 Allowed time between invoice registration and  cancellation as specified by 
MoR 
 Allowed aggregate total value of invoices that can be canceled in a day or a 
month 
 If the rule validation of the request is successful, then the invoice cancellation       
confirmation response is sent to the Taxpayer system. 
 If the limits are exceeded or the request is outside this timeframe, it will 
undergo manual review 
Taxpayer systems should fulfills the following when sending cancellation requests, 
 Taxpayer systems must have been authenticated and a valid access token 
should be in the header 
 Taxpayer systems must sign the request with their private key and include a 
valid certificate 
 Taxpayer systems must encrypt the payload as specified in Security 
Compliance Document

This section offers detailed guidelines for software suppliers, taxpayers, and software developers

records, enhance transaction transparency, and ensure adherence to regulatory standards.

Receipt management is a fundamental element of the e lectronic invoice management system,  A 
receipt serves as concrete evidence that a payment has been successfully processed, offering 
guarantee to businesses, taxpayers, and regulatory bodies. This section will provide an in -depth 
exploration of key aspects of receipt management, including its importance, the step -by-step

directly using APIs for tasks like registering, canceling, and validating invoices. However, before 
any of these actions can be performed, the taxpayer system needs to authenticate with EIMS. This

EIMS. Once generated, these credentials need to be set up within the systems intended to handle 
tasks like invoice registration, cancellation, or verification. Following this process helps ensure the 
systems are secure, efficient, and ready to integrate smoothly with EIMS.
